# ShopSphere backend

Five Node.js + TypeScript microservices that talk to each other only through **Kafka** events, plus a small **Spark Structured Streaming** job that loads analytics events into **ClickHouse**. There are no service-to-service HTTP calls.

```
                   ┌──────────── gateway :8080 ────────────┐
 frontend ──HTTP──►│ CORS · rate limits · JWT check ·       │──HTTP──► one service per request
                   │ session revocation · route permissions │
                   └────────────────────────────────────────┘
 auth-service      product-service     campaign-service        analytics-service (no Postgres)
   identity_db        product_db          campaign_db             │ publish           ▲ /ad counts (SQL)
     │  publish          │  publish          ▲ consume  │ publish   ▼                   │
     ▼                   ▼                   │          ▼         analytics.<event>.v1  ClickHouse
 auth.user.v1      product.v1 ─────────────── ┘    campaign.v1    (12 topics) ──► spark-streaming ──┘
 auth.session.v1 ──────────────────────────► gateway (gateway_db: revoked sessions)
```

- **Separate databases.** Each service has its own Postgres database **and its own login**. The login can't connect to any other service's database. analytics-service is the exception: it stores nothing and only reads ClickHouse.
- **Analytics pipeline.** analytics-service validates each event and publishes it to the topic for its event type. The Spark job (`streaming/`) writes all of them to ClickHouse, and the `/ad` metrics are counted there.
- **Local copies of other services' data.** A service that needs another's data keeps a local *projection* built from that service's events. For example, the campaign service keeps a `products` table (with each product's tenant, creators and timestamps), checks product IDs against it, and never calls the product service.
- **Plain Express in every service.**
- Requires Node 24, which runs the `.ts` files directly; there is no build step.

## Layout

```
packages/contracts/   event types, topic names, roles (shared definitions only)
packages/platform/    shared infrastructure: Express middleware, Drizzle helpers and shared
                      tables (processed_events for the gateway, audit_log), Kafka bus, JWT, health, shutdown
services/<service>/
  drizzle/            SQL migrations generated by drizzle-kit (applied on startup)
  src/
    index.ts          main: database, Kafka, consumers, start the server, shutdown
    app.ts            builds the Express app (service → controller → routes)
    routes/           express.Router(): URL + middleware → controller
    controllers/      (req, res) handlers: call the service, shape the JSON
    services/         business rules and transactions; publish events after commit
    repositories/     database queries (Drizzle query builder)
    validators/       plain functions that return a list of error messages
    events/           Kafka consumers that update local projections
    db/schema.ts      the service's tables: the source of truth for its schema
    db/client.ts      creates the Drizzle client and runs migrations
streaming/            the PySpark job (package event_pipeline) that writes analytics topics to ClickHouse
loadtest/             k6 load test for the analytics path (p99 latency and freshness); results in loadtest/README.md
deploy/helm/          Kubernetes: one Helm chart and release per service, helmfile to deploy all or one (deploy/helm/README.md)
infra/                Postgres and ClickHouse init scripts
scripts/              generate-keys.ts, check-architecture.ts
test/                 architecture test, end-to-end test against real Kafka
```

**Database access.** Every service except analytics-service uses **Drizzle ORM** on its own database. analytics-service queries ClickHouse with `@clickhouse/client`.
- **Schema:** each service's tables live in `src/db/schema.ts`. Tables several services need (`audit_log`, and the gateway's `processed_events`) are defined once in `packages/platform/src/tables.ts` and re-exported from each schema that uses them.
- **Queries:** repositories use the Drizzle query builder.

To change a service's tables:

```bash
# edit services/<service>/src/db/schema.ts, then:
npm run db:generate -w @shopsphere/<service>   # writes a new SQL file to services/<service>/drizzle/
npm run db:generate                            # or: every service (prints "No schema changes" when in sync)
# commit the file; it is applied when the service starts
```

## Run it

```bash
cd backend
npm install
npm run keys                                   # ES256 key pair → keys/ (git-ignored)
docker compose up -d --build                   # Postgres, Kafka, ClickHouse, 4 services, Spark job, gateway on :8080

# Create the storefront's account (tenant): its UUID is VITE_TENANT_ID in
# ../frontend/.env.example. Tiers: free (default), pro, enterprise.
docker compose exec auth-service node services/auth-service/src/cli.ts \
  create-account --name 'Default storefront' --tier free --tenant 5e0f3c2a-8b14-4d6f-9a27-1c3e5b7d9f01

# Create a campaign manager in it. Registration only ever creates standard users.
# All data is per tenant: the manager sees and changes only that tenant's
# products, campaigns and /ad metrics.
docker compose exec auth-service node services/auth-service/src/cli.ts \
  create-user --username maya --password 'correct horse battery' --role campaign-manager --tenant 5e0f3c2a-8b14-4d6f-9a27-1c3e5b7d9f01

# Load the storefront's sample catalog (10 products, 4 active campaigns) into
# that tenant (SEED_TENANT, default: the one above) through the gateway.
# Safe to re-run: products are matched by name and campaigns by title.
# Not needed for tenants onboarded from the frontend: those are seeded automatically.
npm run seed
```

Other CLI commands: `set-role --username maya --role standard-user --tenant <uuid>` and `disable --username maya --tenant <uuid>` (usernames are unique per tenant). Both are published as events, so the gateway picks them up. `create-account` without `--tenant` generates the tenant UUID. `seed-tenant --tenant <uuid>` seeds a tenant onboarded before seeding existed (it needs an `onboarding` user). The seed plan is derived from the tenant ID, so running it again creates nothing twice.

**identity_db** (auth-service) holds:
- `accounts`: one row per tenant (`tenant_id`, `name`, `tier`, `created_at`, `updated_at`);
- `users` and `user_login` (one row per sign-in), each with a mandatory `tenant_id` that references `accounts`.

Rows in `users` and `user_login` are visible only to their own tenant, enforced by Postgres row-level security, so a query that forgets its tenant filter still can't see another tenant's rows. auth-service runs every query in `withTenant()` (`src/db/client.ts`), which sets `app.tenant_id` for that transaction: the storefront's `tenant_id` header before sign-in, the token's `tid` after. With no tenant set, both tables look empty. Sign-up, sign-in and visitor tokens need an existing account (`404 TENANT_NOT_FOUND` otherwise). To look at the data in `psql`, connect as `postgres` (a superuser, which RLS doesn't apply to), or run `SELECT set_config('app.tenant_id', '<uuid>', false)` first.

**Tests.** Postgres, Kafka and ClickHouse must be running (`docker compose up -d postgres kafka clickhouse`). The analytics tests create and drop their own ClickHouse database.

```bash
npm run verify      # typecheck + architecture check + unit/integration tests
npm run test:e2e    # full flow through the gateway with the real Kafka broker
```

**Frontend.** Set `VITE_API_BASE_URL=http://localhost:8080/api/v1` and `VITE_ANALYTICS_MODE=live` in `frontend/.env`. The gateway allows CORS from `http://localhost:5173` (`CORS_ORIGINS`).

## Endpoints (all under `/api/v1`, through the gateway)

|---|---|---|---|

| POST | `/auth/login` | anyone | `{username, password, clientType: web\|mobile}`, with the storefront's `tenant_id` header (usernames are unique per tenant) → `{accessToken, tokenType, expiresIn: 1800, user, session}`. The token carries the user's tenant (`tid`). Rate limited. |
| POST | `/auth/visitor` | anyone | With the storefront's `tenant_id` header → `{visitorToken, tokenType, expiresIn: 1800}`: an anonymous visitor's token for that tenant. It only works for `POST /analytics/events`. Rate limited per IP (`VISITOR_RATE_LIMIT_PER_MINUTE`). |
| POST | `/auth/logout` | signed in | Sets `session_end_time` and publishes `SessionRevoked`. |
| GET | `/auth/me` | signed in | Current user. |
| GET | `/auth/sessions` | signed in | The user's sessions, newest first; `?limit&offset`. |
| GET | `/accounts` | anyone | Every tenant (account): `{items: [{tenantId, name, tier, createdAt}]}`, newest first. For the frontend's onboarding page. |
| POST | `/accounts` | anyone | Demo onboarding: `{name, tier: free\|pro\|enterprise, dummyUsers}`. The server generates the tenant ID and creates the account, an `onboarding` campaign manager and, with `dummyUsers: true`, standard users `user01`–`user10`, **all with the password `test`** (the 12-character rule applies only to `/auth/register`). → 201 `{account, users, password, seed: {products, campaigns}}`. Publishes `UserCreated` for each user and `TenantOnboarded`, from which product-service seeds 10–15 sample products (a random number) and campaign-service 2 active campaigns with 2 and 3 of them (picked at random), created by the `onboarding` user, within seconds. |
| GET | `/products`, `/products/:id` | anyone | One tenant's catalog: the signed-in user's (token `tid`), else the storefront's `tenant_id` header (else 400 `TENANT_REQUIRED`). `?category&includeInactive&limit&offset`. `includeInactive` only works for campaign managers. |
| POST / PATCH | `/products`, `/products/:id` | campaign-manager | `{name, description, price, image?, category?}`; price > 0 with 2 decimals. The product belongs to the manager's tenant; another tenant's product is 404. |
| DELETE | `/products/:id` | campaign-manager | Deactivates; products are never hard-deleted. |
| GET | `/campaigns`, `/campaigns/:id` | anyone | One tenant's campaigns: the signed-in user's (token `tid`), else the storefront's `tenant_id` header (a UUID; else 400 `TENANT_REQUIRED`). Includes `productIds`; `?status&includeArchived&limit&offset`. `includeArchived` only works for campaign managers. |
| POST | `/campaigns` | campaign-manager | `{title, type, description?, status?, startTime?, endTime?, productIds?}`, saved in one transaction. The campaign belongs to the manager's tenant; another tenant's campaign is 404 for every read and write. |
| PATCH | `/campaigns/:id` | campaign-manager | Status: draft→active\|completed, active→paused\|completed, paused→active\|completed. |
| DELETE | `/campaigns/:id` | campaign-manager | Archives the campaign (soft delete). |
| GET / POST | `/campaigns/:id/products` | GET anyone, POST manager | POST `{productIds: [...]}`, of the campaign's own tenant only (another tenant's product is unknown: 409 `PRODUCT_NOT_YET_AVAILABLE`). |
| DELETE | `/campaigns/:id/products/:productId` | campaign-manager | Removes one product. |
| POST | `/analytics/events` | access or visitor token | `{events: [...]}`, 1–100 per request. Returns `accepted`/`rejected` for each event; 429 `TOO_MANY_EVENTS` past 300 events per sender per minute; 503 `EVENTS_NOT_DELIVERED` if Kafka is down. |
| GET | `/ad/:campaignId/clicks` \| `impressions` \| `clickToBasket` | campaign manager | `?from&to` (default: last 30 days, max 366) → `{campaignId, metric, count, period}`, counted in ClickHouse over the manager's own tenant's events only (the token's `tid`; a `tenant_id` header is ignored). An unknown campaign has `count: 0`. |

**Errors** use one format: `{ "error": { "code", "message", "requestId", "details"? } }`. Validation failures return `400 VALIDATION_FAILED` with `details.errors: string[]`.

**Product not yet known to the campaign service.** If a product was created moments ago, the campaign service may not have received its event yet. Creating a campaign with it then returns **409 `PRODUCT_NOT_YET_AVAILABLE` with `Retry-After: 5`**; retry and it will succeed.

**Analytics events.** Each event is `{eventId, eventName, timestamp, campaignId?, productId?, attributionId?, pageName?, featureName?, properties?}`.
- **Who sent it:** every request needs a token. A signed-in user sends their access token; an anonymous visitor gets a visitor token from `POST /auth/visitor` (the storefront does this itself). The tenant and user come from that token, never from a header or the body, so nobody can send events into another tenant without a token for it.
- **Checks on arrival:** the format (UUIDs, a known `eventName`, a `campaignId` on metric events, an `attributionId` on `click_to_basket`), the timestamp (at most 7 days old, at most 5 minutes in the future), at most 300 events per sender per minute (429 `TOO_MANY_EVENTS`, counted per analytics-service instance), and, for metric events only, that the campaign belongs to the sender's tenant and is active and not archived (else that event is rejected with `CAMPAIGN_NOT_ACTIVE`). The campaign check reads `analytics.campaigns`, which analytics-service keeps from `campaign.v1` and caches for 10 seconds, so a new campaign's events count within a few seconds of its creation. Valid events are published to `analytics.<eventName>.v1`.
- **Metric events** (`impression`, `click`, `click_to_basket`) are what `/ad/...` counts. **Storefront activity** (`home_view`, `campaign_navigation`, `product_impression`, `product_click`, `add_to_cart`, `cart_view`, `cart_quantity_update`, `remove_from_cart`, `login_click`) is stored for later analysis and never changes the metrics.
- `user_id` is the access token's user (null for a visitor); `tenant_id` is the token's tenant.
- **Counted in ClickHouse, when the metric is read:**
  - an event sent twice counts once (`uniqExact(event_id)`);
  - a `click_to_basket` counts only if `attributionId` names a `click` on the same campaign, for the same product (if the click had one), by the same user (if both were signed in), within 24 hours after the click, and only once per click and product.
- Events for unknown or inactive campaigns are stored, but nothing on the dashboard shows them.
- Counts are **per tenant**: `analytics.events` is sorted by `(tenant_id, event_name, campaign_id, event_time, event_id)`, and every metric query filters by the caller's tenant, so it reads only that tenant's slice. Tenant IDs are UUIDs everywhere.
- Counts update after Spark's next micro-batch, within about 30 seconds. They are **event totals, not unique customers**.
- **Daily aggregates:** `analytics.campaign_daily_aggregates` has one row per UTC `day`, `tenant_id` and `campaign_id`, with `total_ad_impressions`, `total_ad_clicks` and `total_click_to_basket`, counted by the rules above. `(tenant_id, campaign_id, day)` is unique: every job run rebuilds the table and swaps it in atomically, so there is never more than one row per key. Query it directly, e.g. `SELECT * FROM analytics.campaign_daily_aggregates WHERE tenant_id = toUUID('5e0f3c2a-8b14-4d6f-9a27-1c3e5b7d9f01')`.
  - **The day is when the user acted:** `event_time`, the event's own `timestamp`. Neither the Kafka time nor the time the event was stored is used.
  - **The job runs every hour at :05**, in two ClickHouse refreshable materialized views that run in order:
    1. `campaign_daily_changes_mv` lists the days, per tenant and campaign, that got rows stored (`ingested_at`) since the last run, today included.
    2. `campaign_daily_aggregates_mv` recounts just those days from raw events: distinct impressions and clicks, and basket additions credited per day. Every unchanged row is kept as it was.
  - **Late and reprocessed events are included:** they're stored with a new `ingested_at`, so the next run recounts the day they belong to. One late event costs one day of one campaign, a small range read on the events sort key. A late click also recounts the next day, for baskets credited to it. If the job is down for a while, the next run catches up, because "since the last run" is read from the newest `computed_at`.
  - **Run it now:** `SYSTEM REFRESH VIEW` then `SYSTEM WAIT VIEW` on `analytics.campaign_daily_changes_mv` and `analytics.campaign_daily_aggregates_mv`, in that order.
  - A click credited on two different days counts once on each day.
  - **To rebuild all history,** run `ALTER TABLE analytics.campaign_daily_aggregates UPDATE computed_at = toDateTime64(0, 3, 'UTC') WHERE 1 SETTINGS mutations_sync = 1`, then run the job. The next run treats every day as changed, and the old rows keep serving `/ad` until it swaps in the recounted table.
- **How `/ad` counts a period:** `from` is rounded down to UTC midnight. `to` is rounded up to the next midnight, unless it falls today. Days before yesterday are read from the daily aggregates (one row per day). Yesterday and today are counted from raw events, so the numbers never depend on when the job last ran. A late event for an older day appears in `/ad` after the next hourly run. The `period` in the response shows the rounded bounds.
- **Upgrading an existing ClickHouse volume:** run the commands at the top of `infra/clickhouse/migrations/004_uuid_tenants.sql`. Tenant IDs became UUIDs, so it drops the analytics tables (stored events included) and `init.sql` recreates them. Postgres needs nothing: the auth, product and campaign migrations give existing users, products and campaigns the default tenant `5e0f3c2a-8b14-4d6f-9a27-1c3e5b7d9f01`, and users must sign in again (older tokens have no tenant). `product.v1` and `campaign.v1` events from before the upgrade have no tenant and are ignored, so update each existing campaign once (any change republishes it) for its metric events to count.

## Kafka topics and events

All events share one envelope: `{eventId, eventType, eventVersion, occurredAt, producer, aggregateId, aggregateVersion, payload}`. The message key is `aggregateId`, which keeps events for one product, campaign or user in order.

| Topic | Events | Consumed by |
|---|---|---|
| `auth.user.v1` | UserCreated, UserRoleChanged, UserDisabled | gateway (disabled accounts, stale tokens after a role change) |
| `auth.session.v1` | SessionRevoked | gateway (rejects revoked sessions) |
| `auth.tenant.v1` | TenantOnboarded (keyed by tenant ID; carries the random seed plan: product IDs and the 2 campaigns' IDs and products) | product-service (creates the products), campaign-service (creates the campaigns). Both insert by the planned IDs, so a redelivered event creates nothing twice. |
| `product.v1` | ProductCreated, ProductUpdated, ProductDeactivated | campaign-service (its `products` table) |
| `campaign.v1` | CampaignCreated, CampaignUpdated, CampaignProductAssociated, CampaignProductRemoved | analytics-service (`analytics.campaigns`: each campaign's tenant, and which campaigns metric events may count for) |
| `analytics.<eventName>.v1` (12 topics, one per event name, e.g. `analytics.click.v1`) | AnalyticsEventRecorded; `aggregateId` and key = the client's `eventId`; `payload` = `{eventId, eventName, campaignId, productId, userId, tenantId, pageName, featureName, attributionId, properties, timestamp, receivedAt}` | spark-streaming (→ ClickHouse) |

**How the Node consumers handle messages:**
- The gateway records each `eventId` in `processed_events`, so a redelivered message is applied only once.
- campaign-service has no such table: it applies a product event unless its `aggregateVersion` is older than the copy it holds, so a redelivered event rewrites the same values and a stale one changes nothing.
- A failing message is retried 5 times with exponential backoff, then sent to `dlq.<service>`, and the consumer moves on.

## Health probes and graceful shutdown

Every service exposes three probes. They are served directly by each service, not through the gateway.

| Probe | 200 when | Use it as |
|---|---|---|
| `GET /health/live` | the process can serve HTTP; no dependency checks | liveness: restart the container if this fails |
| `GET /health/startup` | migrations ran and Kafka consumers are subscribed | startup: hold the other probes until this passes |
| `GET /health/ready` | started, not shutting down, and `database` and `kafka` checks pass (2s timeout each) | readiness: take out of the load balancer while failing |

`/health/ready` reports each check, e.g. `{"status":"ready","checks":{"database":"ok","kafka":"ok"}}`. analytics-service checks `kafka` and `clickhouse` instead of `database`. A failing check shows its error message, and the probe returns 503.

**Shutdown on `SIGTERM` / `SIGINT`:**
1. `/health/ready` switches to 503 straight away.
2. The service waits `SHUTDOWN_DRAIN_MS` (default 5s) so the load balancer stops sending traffic.
3. It stops accepting connections, lets in-flight requests finish, and drops idle keep-alive sockets.
4. It closes Kafka (consumers finish their current message, then the producer stops), then the database.
5. It exits with code 0.

If anything hangs past `SHUTDOWN_TIMEOUT_MS` (default 25s), the process exits with code 1. An `uncaughtException` or `unhandledRejection` follows the same steps, skipping the drain, and exits with 1. Compose sets `stop_grace_period: 35s` so Docker doesn't kill the container mid-shutdown.

On Kubernetes, the Helm charts in `deploy/helm/` set these probes and the 35 s grace period.

## Rebuilding a projection (replaying Kafka)

A service's local copy of another service's data can be rebuilt by replaying that service's topics: for example, after its database is recreated. Replaying is safe, because every consumer skips events it has already applied and events older than what it already holds. To replay:

```bash
docker compose stop campaign-service
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --group campaign-service --reset-offsets --to-earliest --all-topics --execute
docker compose start campaign-service
```

The consumer groups are `campaign-service` and `gateway`. To reload ClickHouse from Kafka instead, see `streaming/README.md`. Topics keep events for Kafka's retention period, 7 days by default; set `retention.ms=-1` on the topics if full replays must always be possible.

When the events have expired, or a consumer needs fields that older events lack, product-service can republish every product's current state instead (same versions, so it changes nothing else):

```bash
docker compose exec product-service node services/product-service/src/cli.ts republish
```

## Known limitations

- **No transactional outbox, by choice.** Events are published right after the database commit. If Kafka is unreachable at that moment, the change is saved but its event is lost. The failure is logged as an error, and other services' projections stay stale until that record changes again. This departs from PRD §3.3 / §5.2 and acceptance criterion 10.
- **Revocation is eventually consistent.** After logout, the gateway rejects the token once `SessionRevoked` arrives (under 5 s in tests). Revocation is enforced only at the gateway; the services verify JWT signature, expiry and role themselves, but they don't check revocation.
- **Retries are in-process.** While a message is being retried, it blocks its partition for up to about 3 seconds before going to the dead-letter topic.
- **Public catalog reads, by choice.** `GET /products` and `GET /campaigns` don't need a token, so visitors can browse the store. This departs from PRD §6.2 and §6.3, which say "Authenticated user". All writes still require a campaign manager.
- **Anonymous events can be faked, at a cost.** Anyone can get a visitor token, so counts can still be inflated by a script that keeps fetching tokens. It is limited, not prevented: 10 visitor tokens per IP per minute, 300 events per token per minute, and only active campaigns count. Stopping it entirely needs sign-in for metric events, or bot detection in front of `/auth/visitor`.
- **Tenants are isolated in the data, not in the infrastructure.** Users (and usernames), products, campaigns, events and metrics all belong to one tenant, and every query is scoped by the caller's tenant. Tenants still share the services, databases and Kafka topics.
- **The campaign projection starts from Kafka.** `analytics.campaigns` is built from `campaign.v1`, which keeps events for 7 days. A campaign last changed before that (on a new or rebuilt ClickHouse volume) isn't known, and its metric events are rejected until it changes again (any update republishes its state).
- **Onboarding is open to anyone, by choice.** `GET` and `POST /accounts` need no sign-in, in every environment: anyone can list all tenants' names and IDs, create tenants, and sign in to any onboarded tenant's `onboarding` campaign manager (and demo users) with the password `test`. That suits demos and local development only. Before real tenants use the platform, put these routes behind an admin role (or remove them) and change those passwords.
- **Upgrading to identity_db:** `auth_db` and its login `auth_svc` are now `identity_db` and `identity_svc`. Rename them on an existing `pgdata` volume, then rebuild; the migration creates an account for each tenant that has users:
  ```bash
  docker compose stop auth-service
  docker compose exec postgres psql -U postgres -c 'ALTER DATABASE auth_db RENAME TO identity_db' \
    -c 'ALTER ROLE auth_svc RENAME TO identity_svc' -c "ALTER ROLE identity_svc PASSWORD 'identity_svc_dev'"
  docker compose up -d --build auth-service
  ```
- **Upgrading an existing setup:** Postgres no longer creates `analytics_db`. An existing `pgdata` volume still has it, unused; drop it with `docker compose exec postgres psql -U postgres -c 'DROP DATABASE analytics_db'`. Events stored there before this change aren't moved to ClickHouse.
- **Not implemented this round:** `CampaignMetricUpdated` events, OpenAPI files, refresh tokens, a time-series endpoint, and retention (TTL) for `analytics.events`.
